贡献新任务

提交简短提案先确认价值，再完善任务展开详情 ＋收起详情 −

P1 查看提案、提交简短想法

做什么
先查看已有任务和提案看板，了解领域覆盖与处理进度，再描述新任务的价值。
填写 / 上传
任务名称、研究领域、科学目标、AI 要作出的决策、预期反馈、评价思路与现有资源；可附一个示例，此时不要求完整任务包。
完成后
生成提案编号与“待初审”；看板只展示经确认可公开的摘要、领域和状态。

P2 初审反馈、进入完善

做什么
平台判断科学价值、是否重复及基本可行性，给出继续完善或调整方向的建议。
填写 / 上传
查看初审意见，按需补充简短说明；重复提案可建议合并或协作。
完成后
提案待初审 → 待补充 / 可完善任务 / 未采纳。通过后复用提案信息准备完整任务，仍须经过正式审核。

提案初审确认方向；通过后继续完善完整任务。提案看板只公开经确认的摘要与进度，不展示保密设计和附件。

填写任务考什么、做什么、反馈与评价展开详情 ＋收起详情 −

A1 介绍任务与评测目的

做什么
沿用已通过初审的提案，补充这是什么任务，以及希望检验 AI 的什么科研能力。
填写 / 上传
任务名称、研究领域、背景、任务目标和评测目的；已有信息自动带入，可继续修改。
完成后
形成完整任务草稿，与提案编号关联。

A2 说明 AI 做什么、获得什么反馈

做什么
描述 AI 要作出的决策、可以进行的操作，以及如何根据反馈继续推进任务。
填写 / 上传
给 AI 的任务说明、允许的操作、可见反馈；有预算或停止条件时说明。
完成后
让审核者理解任务从开始到完成怎样进行。
  • 考什么：希望检验 AI 的哪种科研能力？ 用自己的话描述，不必限定在现有任务分类中。
  • 做什么：AI 需要完成什么实验或科学任务？ 说明目标、初始条件和预期交付物。
  • 得到什么反馈：AI 得到什么反馈，如何据此继续决策？ 说明可做的操作与返回的观测；有次数限制时再补充。
  • 怎么评价：怎样判断 AI 完成得好不好？ 给出评价指标、可接受范围或明确判定规则。

沿用已通过初审的提案，写清任务与 AI 的决策过程。具体输入、输出格式和评分依据在下一步补齐；尚未写完可保存草稿。

↓
补充材料输入、输出要求与评测依据展开详情 ＋收起详情 −

A3 明确输入与执行条件

做什么
提供足以开展任务的信息与条件，明确由参与者自行执行，还是由指定实验室执行。
填写 / 上传
初始数据/文件、工具、资源获取方式。涉及湿实验时补充实验协议、实验室、筛选规则与名额、时间安排和返回数据的方式。
完成后
输入与条件可用；筛选、实验和数据返回时间标明预计或已确认，缺项先存草稿或申请协助。

A4 定义输出与评价方法

做什么
说明完成后交什么，以及怎样判断做得好不好。
填写 / 上传
输出内容和格式、评价指标/判定规则；有参考结果时提供，无唯一答案时说明可接受范围。
完成后
明确评价依据；需要时评价过程记录，不能只看最终结果。

A5 补充材料、检查完整性

做什么
把必要材料附齐，检查任务能否开展、评价依据是否清楚。
填写 / 上传
输入附件、任务说明、参考材料或可访问链接；材料来源、使用许可。可附真实试运行记录。
完成后
缺项返回补充；先提想法可申请协助，正式提交前补齐必要内容。

正式提交需要开展任务所需的具体输入和明确输出要求，示例只能辅助解释。参考答案和私密评分材料不放进 AI 可见的输入。材料未齐可申请协助，之后回到同一草稿继续完善。

提交审核预览确认，按反馈修改展开详情 ＋收起详情 −

A6 预览确认、提交审核

做什么
预览全部信息与附件，确认授权和提交条款；也可继续保存草稿。
填写 / 上传
核对本次提交内容及材料使用范围，确认与任务对应的贡献者资料。
完成后
显示提交编号、提交成功与“待审核”；不会立即公开。

A7 分工审核、按反馈修改

做什么
领域审核检查科学合理性与评测价值；执行与技术审核检查条件、材料、反馈机制和评分能否落实。
填写 / 上传
查看各类审核意见，修改任务说明、材料或评价方法后重新提交；平台汇总给出处理结论。
完成后
完整任务通过 → 待发布；需修改 → 返回相关步骤；未通过 → 显示原因。提案初审不替代本次审核。

草稿 → 待审核 → 待修改 / 待发布 / 未通过。需修改时返回“填写任务”或“补充材料”，完成后重新提交；平台提供具体原因与反馈。

↓
发布与维护公开范围、署名与纠错展开详情 ＋收起详情 −

A8 确认公开范围、发布任务

做什么
平台与贡献者确认发布版本、公开材料和署名，将任务纳入评测。
填写 / 上传
逐项确认任务说明、设计/方法、数据、过程记录和署名的公开范围及时间；明确仅审核可见的材料和保留的隐藏评分内容。
完成后
显示“已发布”、版本与任务链接；参与者可提前查看实验规则、公开约定及纠错入口。

A9 发布后的纠错与维护

做什么
任务页提供问题反馈入口，关联作者和审核者；平台判断是否需要修正、暂停使用或重新评测。
填写 / 上传
问题所涉任务/版本、现象、复现条件或证据、建议修改；作者补充说明或提交修订。
完成后
已反馈 → 处理中 → 修订审核 → 新版本 / 关闭并说明。保留旧版本与变更记录，说明对既有成绩的影响并通知受影响者。

审核通过后先进入待发布，确认版本与公开范围后再发布。发现问题可随时反馈；公开后保留明确的纠错入口、负责人和版本记录。

初审需补充：修改提案；完整审核需修改：返回任务或材料。发布后可提交纠错。

参与已有任务 / 提交结果

选择已有任务确认版本与执行方式展开详情 ＋收起详情 −

B1 选择已有任务与版本

做什么
阅读该任务的输入、允许操作、交付要求、执行方式和结果公开约定。
填写 / 上传
关联任务及版本；若涉及湿实验，查看筛选名额、排期及数据返回安排。
完成后
待执行则进入执行与实验进度；已有符合该版本要求的完整结果可直接整理上传。

已有完整结果可直接进入“上传结果与记录”；否则先按任务约定自行执行或申请实验。

↓
执行与实验进度按需筛选、排期与返回反馈展开详情 ＋收起详情 −

E1 确认执行方式、申请实验名额

做什么
按任务约定自行执行，或提交待测试设计/执行方案，申请指定实验室的湿实验。
填写 / 上传
任务与版本、待测试设计或方案、必要说明；先阅读筛选依据、名额、实验协议、公开约定及预计时间，再确认申请。
完成后
自行执行可直接开始；湿实验申请 → 待筛选 → 入选待排期 / 候补 / 未入选。提交成功不保证入选，未入选不生成实验成绩。

E2 跟踪执行、获得反馈并继续决策

做什么
自行执行者按任务规则开展操作并记录进度；指定实验室按该任务统一协议执行入选方案。AI 在允许的轮次内根据观测调整下一步。
填写 / 上传
记录做了什么、观察到什么、AI 如何据此决策；保留设计/方案版本、执行条件，以及正常结果、负结果和执行异常。湿实验补充批次与协议版本。
完成后
自行执行：执行中 → 获得反馈；指定实验室：待排期 → 实验中 → 数据质检 → 反馈已返回。两种方式都可按规则继续决策与执行，达到停止条件后整理结果；延期或异常说明后续安排。

E3 整理全部已执行记录

做什么
按预先公布的规则归档已测试设计的成功与失败结果，并区分有效负结果与实验技术失败。
填写 / 上传
测量数据、质量标记、失败/异常原因（如已知）和可用过程记录；尚未得到的数据标为缺失，不填成零。
完成后
有效负结果保留并按规则评价；技术失败按约定决定复测或标记无有效成绩，再进入结果确认。

湿实验筛选的对象是待测试设计或执行方案，与左侧新任务提案初审分开。名额和日期由具体任务公布；每一轮反馈是否可用于下一步、何时结束，也由任务规则约定。

↓
上传结果与记录实际产物、过程证据与执行信息展开详情 ＋收起详情 −

B2 整理结果、证据与执行信息

做什么
汇总实际完成的产物和过程记录，说明使用什么方法或系统完成；实验室已返回的数据可直接关联。
填写 / 上传
结果文件/数据、必要过程记录、模型/工具或执行方式、关键条件；已测试设计的成功与失败均保留。
完成后
形成可核验的结果草稿；已归档的实验数据无需重复上传。

必要材料由所选任务决定。应能核验实际执行过程；补充截图或日志是否必需，以该任务要求为准。

校验、确认与评分检查材料，确认后进入评测展开详情 ＋收起详情 −

B3 校验材料、确认提交

做什么
检查任务关联、文件完整性和必要信息，修复问题后确认提交。
填写 / 上传
查看缺项提示，核对本次结果与材料授权；确认实际提交内容。
完成后
显示提交成功及“待评测”。上传文件后仍需最终确认。

B4 平台评分、处理反馈

做什么
平台按照该任务的规则核验和评分；需要澄清时要求补充证据。
填写 / 上传
查看得分与处理意见；有缺项则回到 B2/B3 补充并重新提交。
完成后
已评测 / 待补充 / 未通过；显示相应反馈或原因。

上传文件不等于提交完成。校验后由本人确认，再进入待评测；评分由平台处理。需要补充时回到“上传结果与记录”，补齐后重新确认。

↓
展示与纠错按约定公开，保留更正记录展开详情 ＋收起详情 −

B5 按约定公开结果

做什么
平台核对评分与数据质量，按参与前公布并确认的范围和时间公开结果；湿实验保留成功与失败记录。
填写 / 上传
列明将公开的成绩、任务版本、设计、方法、测量值、过程记录与署名；注明保留材料、有效负结果及技术失败标记。
完成后
获准后展示；已评分不等于自动公开。未入选或未执行项单独标明，不作为已测试失败结果。

B6 结果纠错与复核

做什么
个人状态页和公开结果页均提供问题反馈入口，由平台联系相关作者、实验室或审核者处理。
填写 / 上传
结果编号、任务版本、异议内容与证据；说明是否影响数据、评分或归属信息。
完成后
反馈 → 核验 → 更正 / 复测或重评 / 保持原结论并说明。保留更正记录及版本关联，通知受影响者。

已评分与已公开是不同状态。公开范围在参与前说明；保留已测试设计的失败记录，避免只展示成功项。个人可查看状态、反馈问题并跟踪复核。

实验反馈 → AI 继续决策；材料缺项 → 补齐后确认；结果有误 → 申请复核。

草稿可随时保存；两个入口均可查看处理状态与修改意见。步骤与状态为 AISLE 的设计建议。

先提案，再完善：简短提案初审通过后，再准备完整任务。草稿随时可存，材料未齐可申请协助。完整任务正式提交前须具备开展和评价所需的内容；上述步骤与状态均为 AISLE 设计建议。

Proteinbase / Adaptyv · 真实湿实验评测

网站已确认：提交设计 → 筛选 → 湿实验测试 → 发布结果。入选设计由同一实验室按统一协议测试；每项比赛有自己的筛选规则、名额和时间表。已测试设计的序列、预测结构、设计方法和实验测量值公开，包括未成功的设计。

AISLE 如何采用：已补入任务材料中的实验安排、参与分支的筛选与进度、全部已测试结果的记录，以及发布前的公开范围确认。

主要收集待测试设计，不能直接套成新任务的入库审核。页面的周次和名额是比赛示例，不作为 AISLE 的固定承诺。

Terminal-Bench-Science · 任务提案、审核与维护

网站已确认：先提交提案，人工反馈并批准后制作任务包与提交 PR；领域和技术审核并行，之后由项目负责人最终确认。提案看板展示进度和领域覆盖；任务修正请求会到达作者和审核者，发布后仍需维护。

AISLE 如何采用：已补入简短提案与看板、提案通过后完善任务、分工审核，以及发布后的问题反馈和版本维护。

其领域专家资格、确定性程序测试、容器格式和共同作者条款属于该项目，不自动成为 AISLE 的要求。

Codabench · 评测运行与成绩管理

网站已确认：支持本地运行后上传结果，也支持上传代码由平台执行。可设置反馈阶段与最终阶段，限制最终提交次数或自动迁移到最终测试；参考答案隐藏。代码提交可隐藏输入数据，结果提交通常需要参与者获取测试输入。

AISLE 如何采用：执行责任已要求写清。分阶段评测、正式提交次数和平台统一运行先保留为后续配置建议。

隐藏参考答案与隐藏测试输入并非同一件事；不能把“全部测试输入隐藏”套到所有上传结果的任务。

后续配置建议 · 正式收集评测成绩时再加入

以下尚未设为统一提交门槛，按任务需要讨论和启用。

  • 调试与正式评测分开：可以先开放小样例或验证环境调试，再使用独立正式评测条件；正式收集成绩时再按任务配置。
  • 设置正式提交规则：提前说明正式提交次数、失败提交是否计数、能否重试，以及返回哪些正式反馈；此处不指定统一次数。
  • 明确平台运行责任：以后若支持代码/Agent 上传，应由平台校验后执行并产生结果；不能要求参与者先上传尚未生成的结果。
  • 保护评测依据，同时保留任务反馈：参考答案和私密评分内容保留在评测侧；测试输入是否隐藏取决于执行模式。AI 在任务内获准取得实验反馈、继续决策，与参与者反复使用正式成绩调参应分开管理。

1. 适配度、案例与协助
ALE

任务标准为复杂、真实专业工作、结果可验证。提供正反例、视频和完整案例；目标应是端到端工作，而非单个简单操作。

ALE

适配度预评估需登录；只返回建议，不创建或保存任务。若无法定义客观评分，可上传原始项目文件，由团队寻找可验证子任务。

ALE

评分判断路径：确定性结果 → 提供输出；数值可评 → 数值指标＋原输出；可用简单问答判定 → QA/截图＋原输出；仍不行 → 项目文件与协助。

ASI

强调科学意义、客观评分、可复现、自包含与自主性挑战。相同参数和种子应产生稳定参考结果。

2. 输入、输出、环境与任务包
ALE

五类核心材料：任务说明、原始输入、软件、参考输出、评分标准。软件需名称/精确版本、OS；可附依赖、Docker 或安装脚本。

ALE

Aisle 建议

实验类沿用目标、输入、输出、评测四个核心部分，补充必要实验条件与实测数据；不把软件/OS 等字段强制套用于湿实验。

3. 难度自测与 B1–B4：不能统一写成选填
ALE

本地自测是建议，不是强制提交条件。自动 AI 初审也是辅助信号，不是必须通过的门槛；团队继续检查完整性、可行性、参考结果真实性、难度和贡献数量。

ALE

当前 FAQ 按 GPT-6 Astra 与 Claude Opus 5.5 的平均分区分难度：near-term < 0.5，last-exam < 0.1。这里沿用该页的分数尺度，不和 ASI 的 0–100 分混用。

ASI

B1：完整科学背景、方法、方程与步骤；B2：方法和约束，具体实现开放；B3：目标、输入、约束、输出，由执行者选方法；B4：保留完整 B3，加入正确但非必要的信息，测试干扰稳健性。

ASI

必须先完成预提交验证，再用同一执行框架、模型、推理强度和运行设置跑完 B1–B4。提示须模型无关，不针对某一框架或模型编写。

ASI

当前指南指定的合格测试配置：Codex CLI / GPT-5.6 Sol / ultra；Claude Code / Claude Opus 4.8 / max；或 Claude Code / Fable 5 / max。仅为参考站规则记录，不是本任务的模型设置。

ASI

四个分数须为 0–100 的有限数，B1 ≥ B2 ≥ B3 ≥ B4；B3、B4 各自严格小于 40，B1/B2 无单独上限。记录配置、四个成绩、阶段耗时、环境、评分重放证据，使用 OS 沙箱。

ASI

贡献者提供的自测证据在审核时标为 Not platform-verified；它与平台正式评分分开。

Aisle 建议

基础完整性/可评测性检查列为必做。是否引入 B1–B4 及相应门槛另行决定，不能把计算评测的硬性配置直接套用到湿实验。

5. 审核、退回修改与任务发布
ALE

提交后先自动初审，再由团队检查完整性与可行性，可能联系贡献者补材料。参考输出须来自真实执行；伪造会影响署名资格。

ASI

提交提案默认私密。维护者检查科学价值、可复现性、打包质量、评分可靠性和基准适配度；可通过、要求修改或拒绝。

ASI

公开需同时完成四关：审核确切冻结版本 → 管理员审核并合入私有基准 Draft PR → 仅可公开文件进入公共 main 且 status: final → 人工更新并审核网站清单。

ASI

test、in_development、needs_further_development、abandoned 均不自动出现在网站。审核通过、建立 PR、文件进仓库都不等于发布；目录和排行榜更新由人工控制。

Aisle 建议

状态与下一步并列展示；草稿可继续编辑，待修改返回任务材料，审核通过进入待发布。收到拒绝显示原因，不默认进入发布。

6. 结果包、校验、正式评分与排行榜
ASI

先用 asibench run --no-score 生成公开基准输出，再由 asibench submit --results-dir out/ 打包和上传。不要手工构建、改名重打包或上传 ZIP。

ASI

没有配置上传 endpoint 时只生成本地包并显示 NOT SUBMITTED；不能把本地生成成功当作已提交。上传成功只创建私密草稿，需打开返回链接并点击 Confirm。

ASI

结果包为 schema v1 的 .tar.gz，包含且仅包含一个 manifest.json、至少一个实例、结果与输出；运行元数据和框架任务快照可选。每个文件记录相对路径、字节数、SHA-256。

ASI

实例记录任务/实例标识、B 层级、尝试次数、状态、agent、模型/effort、沙箱与输出。缺失输出须如实标为 missing，不伪装成完整；额外文件在确认页报告。

ASI

门户拒绝绝对/父级路径、链接、设备等非普通文件，限制压缩与解压大小和文件数；校验 manifest、大小和哈希，汇总每实例缺失输出。不得包含私密参考答案和评分配置。

ASI

顺序：上传 → 完整性校验 → 输出齐全性检查 → 本人确认 → 维护者用确切上传包和私密参考集评分 → 决定 → 发布。公共 seed42 结果要求 effective sandbox 为 os；其他模式评分前拒绝。

ASI

状态：uploaded 私密待确认；received 已确认待处理；scored 已评分未公开；published 已公开；rejected 不合格并显示原因。正式均分为 0–100，仅在兼容沙箱/运行分组中比较。

Aisle 建议

结果提交保留同样的校验、确认、评分、发布顺序；湿实验的结果与证据格式由对应任务定义，不要求实验贡献者套用 ASI 软件结果包。

ALE

Aisle 建议

在开始页面列出署名/致谢政策、使用许可、隐私说明与帮助入口；只承诺团队实际提供的权益，不照搬奖金与论文署名门槛。
